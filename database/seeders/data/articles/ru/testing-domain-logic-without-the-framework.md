Самые ценные тесты покрывают правила, без которых бизнес не работает, — а эти правила редко нуждаются в базе данных, HTTP-слое или контейнере фреймворка.

## Отодвиньте фреймворк к краям

Если сущность зависит от ORM, каждый тест правила тянет за собой инициализацию приложения. Держите доменные объекты свободными от инфраструктурных импортов — и весь набор будет выполняться за миллисекунды.

```php
$invoice = Invoice::issue(
    new InvoiceNumber('2026-0042'),
    new Money(1250, 'EUR'),
);

expect($invoice->toTotal()->amount())->toBe(1250);
```

> [!IMPORTANT]
> Доменный тест, которому нужен контейнер, обычно проверяет связывание зависимостей, а не правило.

## Валидация живёт в объектах-значениях

Создать невалидный объект должно быть невозможно. Тогда каждый последующий тест может считать входные данные валидными.

| Правило | Кем обеспечивается |
| --- | --- |
| Положительная сумма | `Money` |
| Непустой заголовок | `Title` |
| Допустимый переход статуса | `Invoice` |

## Интеграционные тесты для стыков

Один интеграционный тест на репозиторий или эндпоинт доказывает, что маппинг работает. Остальные остаются быстрыми и сфокусированными.

![Тестирование домена](/assets/demo/articles/testing.svg)

> [!TRADEOFF]
> Чистый доменный код многословнее на старте. Награда — набор тестов, который можно гонять при каждом сохранении, а не раз в день.

## Фикстуры как построители

Построители делают тесты читаемыми и прячут те части подготовки, которые конкретному тесту не важны.

```php
$invoice = InvoiceFactory::new()->overdue()->make();
```
